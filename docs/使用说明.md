# 使用说明

Rust TLS 1.3 加密 TCP 隧道中转系统 —— 从零部署到日常运维的完整说明。

---

## 1. 这套系统做什么

在两台服务器之间建立加密隧道，把一台机器上的 TCP 端口透明转发到另一台机器后面的服务。

```
用户 ──▶ TCP ──▶ 上海入口 ──▶ TLS 1.3 加密隧道 ──▶ 香港出口 ──▶ TCP ──▶ 目标服务
```

**只处理 TCP。** 没有 UDP 监听、没有 UDP over TCP、没有 QUIC。上层协议如果需要 UDP（例如 Dodobird），它自己已经把 UDP 封装进 TCP 流了，到本系统这里看到的始终是一条 TCP 字节流。

中转层不解析载荷内容。里面跑的是 Dodobird 帧、VLESS 还是普通 HTTP，对它都一样，都是不透明字节流。唯一的保证是：

> **进去的字节流 == 出来的字节流**，顺序不变、内容不改、连接生命周期（含半关闭）完整保留。

### 三个进程

| 组件 | 作用 | 装在哪 |
|---|---|---|
| `tunnel-control` | 控制面 + Web 管理面板 | 一台管理机 |
| `tunnel-agent` | 数据面，转发流量 | 每台中转机 |
| Web 面板 | 浏览器界面 | 由 control 提供 |

agent 只有一个程序，靠配置决定角色：`entry`（入口）、`exit`（出口）、`both`（两者兼任）。

---

### 两种转发模式

先分清这两种，它们决定你需要几台机器：

| | 直连转发 | 隧道转发 |
|---|---|---|
| 机器数 | **1 台** | **2 台**（两端各一） |
| 路径 | 用户 → 转发机 → 目标 | 用户 → 入口 ══加密══▶ 出口 → 目标 |
| 本系统加密 | 无 | TLS 1.3 |
| 需要证书 | 不需要 | 需要（私有 CA） |
| 需要隧道地址 | 不需要 | 需要 |
| 典型场景 | 三网优化机直转落地；IEPL 只给一端 root | 自有两地机器，跨境加密 |

两种模式下被转发的载荷通常都已由上层协议（VLESS/Trojan 等）加密。隧道模式的加密买到的是**隐藏已加密流量的形状**（防 TLS-in-TLS 指纹），而不是"给明文加密"。

### 三层概念

```
设备组（入口 / 出口）        ← 令牌挂在这里，一条命令可加多台机器
   └─ 机器                  ← agent 自注册进来
        └─ 隧道地址          ← 出口机器的属性，仅隧道模式需要
线路                         ← 直连模式引用一个组；隧道模式引用「入口组 → 出口组」
```

| 概念 | 是什么 | 在哪管理 |
|---|---|---|
| **设备组** | 入口或出口机器的集合。注册令牌挂在组上 | 「设备组」页 |
| **机器** | 组内的一台服务器。用一键对接命令自注册 | 组详情页 |
| **隧道地址** | 入口拨向出口时用的地址（IEPL / 公网） | 组详情页 |
| **线路** | 转发规则：入口组监听什么、出口组拨向哪 | 「线路」页 |

关键在于**线路引用组，不引用单台机器**。所以组内加机器、换机器、下线一台，线路配置都不用动 —— 组内每台机器都会承载这条线路。

## 2. 快速上手（单机测试）

想先在一台机器上跑通看看，最快的路径：

```bash
cd tunnel

# 编译 + 安装控制面和 agent
sudo ./scripts/install.sh both

# 启动控制面
sudo systemctl enable --now tunnel-control

# 取出初始管理员密码（只打印一次）
sudo journalctl -u tunnel-control | grep -A4 '初始管理员\|Initial administrator'
```

浏览器打开 `http://127.0.0.1:8080`，用上面的用户名密码登录，**先改密码**（未改密前所有写操作都会被拒绝，这是刻意的）。

控制面安装脚本已生成隧道 CA。后续用面板的一键对接命令安装入口和出口，脚本会自动领取各自所需的证书。

然后在面板里：建两个设备组 → 用一键对接把机器加进来 → 给出口机器加隧道地址 → 建线路。详见第 5 节。

## 3. 生产部署

### 3.1 控制面（管理机）

```bash
cd tunnel
sudo ./scripts/install.sh control
```

脚本会做这些事：编译二进制、建 `tunnel` 系统用户、生成 `/etc/tunnel-control/config.toml` 并**自动填入随机的 `jwt_secret` 与 `tunnel_psk`**、初始化 SQLite、安装 systemd 单元、构建并部署 Web 面板。

脚本是幂等的。重复执行不会覆盖已有配置，也**不会重新生成密钥** —— 重新生成会让所有已发出的会话失效、所有 agent 握手失败，这是"重跑一次安装脚本"最容易引入的故障。

启动：

```bash
sudo systemctl enable --now tunnel-control
sudo journalctl -u tunnel-control | grep -A4 '初始管理员\|Initial administrator'
```

默认只监听 `127.0.0.1:8080`。对外暴露请用 nginx 终结 TLS（配置样例见 `docs/deployment.md`），不要直接把 8080 开到公网。

### 3.2 隧道证书

入口和出口之间用私有 CA 签发的证书互相验证。**必须用私有 CA，不要用公共 CA** —— 配置里设了 `ca_path` 后系统信任库会被忽略，这正是想要的：否则任何一家公共 CA 都能冒充你的出口节点。

Docker 部署脚本会在首次部署时创建 `certs/ca.pem` 和 `certs/ca.key`，并挂载到控制面。重复部署会沿用原有 CA。原生 `install.sh control` 则在 `/etc/tunnel/` 创建 CA。**请备份 CA 私钥**：控制面需要它为新出口签证书，丢失后不能继续签发。

若使用手动部署或需要手工签证书，仍可执行：

```bash
# 建 CA（只做一次，ca.key 须安全备份）
./scripts/gen-certs.sh ca

# 为出口节点签发服务端证书。把域名和所有会用到的 IP 都写进去。
./scripts/gen-certs.sh server exit.internal 10.20.0.2 203.0.113.9
```

脚本会打印该证书怎么部署、以及面板里 `tls_server_name` 该填什么。

需要双向认证（mTLS）时再签一张客户端证书：

```bash
./scripts/gen-certs.sh client entry.internal
```

然后在出口的 agent 配置里设 `require_client_auth = true`，入口填上 `client_cert_path` / `client_key_path`。这样攻击者既需要 CA 签发的客户端证书，又需要 PSK。

### 3.3 每台中转机 —— 一键对接

**不需要手工装 agent、不需要手抄令牌。** 流程是：

1. 面板 →「设备组」→ 新建一个组（入口或出口）
2. 点该组的「一键对接」，复制弹出的命令
3. 到目标服务器上以 root 执行

```bash
bash <(curl -fsSL http://管理机地址:8080/api/agent/install.sh) \
  -t <令牌> -u http://管理机地址:8080
```

脚本会自动完成：下载安装 agent、从控制面领取 CA、在出口本机生成私钥并领取签发证书、写出配置（权限 0600）、安装并启动 systemd 服务、agent 自行向组注册。执行完回到面板，该机器就会出现在组内。出口私钥不会传到控制面。

**同一条命令可以在多台机器上执行**，它们全部加入同一个组 —— 这是令牌挂在组上而非单机的直接收益。

脚本还会询问是否应用网络优化，详见 3.4。

入口机器只需 CA，出口机器所需的 `exit.pem` 和 `exit.key` 由脚本自动配置。自动签发的出口证书使用控制面分配的 TLS 名称，入口配置会自动采用此名称。

#### 关于令牌轮换

每次点「一键对接」查看命令，都会**重新签发令牌，旧令牌立即失效**。

这是刻意的取舍：库里只存令牌哈希、无法还原明文，所以"查看命令"必须重新签发。要么明文存令牌（数据库泄露即凭据泄露），要么每次查看都轮换 —— 选了后者。

影响：组内**已在线的机器不会掉线**（它们已完成注册），但重装或新增机器必须用最新的命令。

### 3.4 网络优化

一键对接脚本会询问是否应用网络优化。**改动前会逐项打印当前值与目标值**：

```
将应用以下内核参数：
  net.core.somaxconn               128 → 4096
     作用：accept 队列上限。过小时连接风暴会让内核静默丢 SYN，
           客户端表现为连接超时而日志里什么都没有。
  net.ipv4.tcp_congestion_control  cubic → bbr
  net.core.default_qdisc           → fq
     作用：BBR 在有非拥塞丢包的长肥链路上通常优于 CUBIC。
           风险：与 CUBIC 流共享链路时公平性有争议；专线上无此问题。
  LimitNOFILE (systemd)            1024 → 65535  已写入服务单元

以下仅提示，不自动修改：
  tcp_rmem / tcp_wmem —— 这是每个 socket 的上限，会按连接数倍增。
    在 10000 连接下把 max 设成 16MB 理论可占 160GB 缓冲，足以触发 OOM。
  rp_filter —— 双网卡 IEPL 主机需要设为 2（宽松），但改错会静默丢包。

继续应用上述低风险参数？ [y/N]
```

只动低风险项，`tcp_rmem`/`wmem` 与 `rp_filter` 仅提示不改 —— 前者按连接数放大内存，后者改错的故障表现极难排查，都该由管理员按实测决定。

非交互执行时用 `--tune --yes` 自动确认，或 `--no-tune` 完全跳过。

## 4. IEPL 双网卡专线配置

**这一节必须在配置 endpoint 之前读完。** 内核路由没配对的话，源地址绑定不会走私网网卡，而故障表现是"连接建立不起来、日志里什么异常都没有"—— 这是整套系统里最难排查的问题。

### 4.1 典型拓扑

```
       用户                                          目标服务
        │                                               ▲
        ▼                                               │
 ┌──────────────────┐                        ┌──────────────────┐
 │    上海 入口     │                        │    香港 出口     │
 │ eth0 203.0.113.1 │◀── 公网，用户接入      │ eth0 203.0.113.9 │── 公网出站
 │ eth1 10.20.0.1   │───── IEPL 专线 ───────▶│ eth1 10.20.0.2   │
 └──────────────────┘      隧道流量          └──────────────────┘
```

三个地址、三种用途，**绝不能混用**：

| 地址 | 用途 | 配在哪 |
|---|---|---|
| `203.0.113.1`（沪 eth0） | 用户接入 | 路由的 `监听地址` |
| `10.20.0.1` → `10.20.0.2`（eth1） | 隧道传输 | endpoint 的 `源 IP` → `地址` |
| `203.0.113.9`（港 eth0） | 业务出站 | 路由的 `出站源 IP` |

节点的"公网地址"字段**仅用于展示**，系统永远不会用它拨隧道。隧道地址是 endpoint。把两者混为一谈是这类系统最常见的翻车方式，所以数据模型里刻意把它们分开。

### 4.2 内核路由（在入口机上执行）

第二条默认路由不能放在主表里，要给专线单独一张表，再用规则按源地址选表：

```bash
# 给路由表命名，只需一次
echo "100 iepl" >> /etc/iproute2/rt_tables

ip route add 10.20.0.0/24 dev eth1 src 10.20.0.1 table iepl
ip route add default via 10.20.0.254 dev eth1 table iepl
ip rule add from 10.20.0.1 lookup iepl
```

**`ip rule` 这行是关键**，它才是让 `bind(10.20.0.1)` 真正从 eth1 出去的原因。

验证：

```bash
ip route get 10.20.0.2 from 10.20.0.1     # 应该显示 dev eth1
ip route get 8.8.8.8 from 203.0.113.1     # 应该显示 dev eth0
```

### 4.3 rp_filter —— 最容易踩的坑

反向路径过滤会丢掉"从内核认为不该收到的网卡进来的包"。双网卡加策略路由的场景下，它会静默丢弃合法流量：

```bash
# 0=关闭 1=严格 2=宽松
# 宽松模式下只要源地址能从任一网卡到达就放行，这是多网卡主机的正确选择
sysctl -w net.ipv4.conf.all.rp_filter=2
sysctl -w net.ipv4.conf.eth1.rp_filter=2
```

**用 `2` 而不是 `0`** —— 宽松模式仍会丢弃真正不可路由的源地址，保留了部分防伪造能力。

单网卡主机不要动这个参数，严格模式在那里是合理默认值。

持久化到 `/etc/sysctl.d/10-tunnel.conf`。

### 4.4 源地址绑定 vs SO_BINDTODEVICE

两种机制不可互换，系统两者都支持，默认用前者。

**`bind(源IP)`（推荐）** —— 连接前绑定本地源地址，内核会选一条源地址匹配的路由。

- 无需任何特权
- 全平台可用
- `ss -tnp` 里能正确看到
- 依赖路由表正确：配了策略路由后，源地址**就是**选路依据

失败表现清晰：地址不在本机任何网卡上时 `bind` 直接报 `EADDRNOTAVAIL`，agent 会把出错的地址和提示一起打出来。

**`SO_BINDTODEVICE`（备选）** —— 无视路由表，直接把 socket 钉在指定网卡上。

- **仅 Linux**
- **需要 `CAP_NET_RAW`**（systemd 单元里要加 `AmbientCapabilities=CAP_NET_RAW`，或用 root）
- 会绕过策略路由，出问题很难定位

只有一种情况真正需要它：两块网卡上有重叠/重复的子网，此时源 IP 已不能唯一确定路径。其余情况都用源 IP。

### 4.5 ARP flux

两块网卡接在同一个二层网段时，Linux 默认会用任意网卡回应任意本地地址的 ARP，对端可能学到错误的 MAC：

```bash
sysctl -w net.ipv4.conf.all.arp_announce=2
sysctl -w net.ipv4.conf.all.arp_ignore=1
```

两块网卡在不同网段时不需要动。

### 4.6 系统不会碰你的网络配置

agent 只**采集**网卡信息用于展示，面板只让你**选择**地址。涉及 `ip rule`、`ip route`、`sysctl` 的一切都由管理员手工确认后应用 —— 程序不会擅自修改服务器网络配置。

## 5. 面板操作

### 5.1 设备组

新建时填写：

| 字段 | 说明 |
|---|---|
| 名称 | 如 `香港出口` |
| 类型 | `入口`（接用户、拨隧道）/ `出口`（终结隧道、拨目标）/ `入口+出口` |
| 地区 | 如 `hk`，仅用于展示与排序 |
| 备注 | 可选 |

**类型决定组内机器的角色**，且 agent 自报的角色会被收敛到组类型允许的范围 —— 出口组里的机器即使本地配置写了 `both`，也只会得到 `exit`。这防的是配置漂移：否则它会去监听入口端口，而那条线路的入口在别的组。

已被线路引用的组**不能改类型**，因为 inbound 组突然变 outbound 会让引用它的线路失去入口。

创建后会立刻弹出一键对接命令。之后随时可以在列表里点「一键对接」再次取得（会轮换令牌，见 3.3）。

### 5.2 组详情页

一个组内的全部管理都在这里：

- **组内机器** —— 每台的探针数据：CPU、内存、连接数、实时上下行、版本、运行时长、最后心跳。可单独移除某台机器（线路不受影响，组内其余机器继续承载）。
- **隧道地址** —— 按机器分列。点某台机器的「加隧道地址」为它添加。
- **隧道状态** —— 组内所有机器上的隧道：状态、RTT、承载流数、收发字节、重连次数。
- **网卡** —— 各机器的网卡与地址，只读。
- **相关线路** —— 引用本组的线路，标注本组在其中是入口还是出口。

### 5.3 隧道地址

隧道地址是**入口拨向出口时使用的地址**，属于出口机器 —— 不是机器的公网地址。

IEPL 主备的典型配法 —— 同一台出口机器上加两个地址，同一个监听进程，两条路径：

| 字段 | IEPL（主） | 公网（备） |
|---|---|---|
| 地址 | `10.20.0.2` | `203.0.113.9` |
| 端口 | `5000` | `5000` |
| 类型 | `iepl` | `public` |
| 优先级 | `主` | `备` |
| 网卡 | `eth1` | `eth0` |
| 源 IP | `10.20.0.1` | 留空 |
| TLS 名称 | 留空（自动签发） | 留空（自动签发） |

**源 IP** 由入口在连接前绑定，是强制隧道走 IEPL 网卡的手段。

**TLS 名称**：一键对接的出口会自动获得证书，入口拿到的配置也会自动使用正确名称。仅手动签发证书时需要填写，且同一出口的两个地址须使用证书里的同一名称。

出口组有多台机器时，每台各自配自己的隧道地址。一条线路可以同时引用它们，隧道池在这些地址间做负载与故障转移。

### 5.4 线路

线路有两种模式，先选对模式再填字段。

#### 直连转发（单机）

```
用户 ──▶ 转发机:端口 ──▶ 落地机:443
```

只需一台机器。适用场景：

- 一台三网优化机直接把端口转到落地机
- **IEPL 商家只给你出口 root**，国内入口只给一个转发 IP（那边装不了 agent，因此不可能建隧道）
- IEPL 商家给一台双网卡机器（专线段由商家网络承载，你不需要自己建隧道）

| 字段 | 示例 | 说明 |
|---|---|---|
| 转发模式 | `直连转发` | |
| 设备组 | `香港转发` | 转发机所在的组 |
| 监听地址 | `0.0.0.0` | |
| 监听端口 | 留空 | 留空则随机分配，见下文 |
| 目标主机 | `233.21.21.21` : `443` | **你的落地机** |
| 出站源 IP | `203.0.113.9` | **双网卡必填**，见下 |

不需要出口组、不需要隧道地址、不需要证书、不需要隧道池。

**本系统不加密这条链路。** 但被转发的通常是 VLESS/Trojan 这类自带 TLS 的协议流量 —— 字节本来就是密文，再包一层只是浪费 CPU。真正明文的只有 TCP 头部（源/目的地址），而那个信息无论如何都藏不住。

**双网卡时出站源 IP 必填**：不绑公网源地址，内核可能把去落地机的流量也从专线网卡送出去，绕回对端再出国，延迟翻倍甚至不通。

#### 隧道转发（两端各一台）

```
用户 ──▶ 入口组:端口 ══TLS 1.3══▶ 出口组 ──▶ 目标
```

| 字段 | 示例 | 说明 |
|---|---|---|
| 转发模式 | `隧道转发` | |
| 入口组 | `上海入口` | 组内每台机器都会起这个监听 |
| 监听端口 | 留空或指定 | |
| 出口组 | `香港出口` | |
| 目标主机 | `127.0.0.1` : `8443` | 出口机器视角看到的服务 |
| 隧道地址 | IEPL 在前，公网在后 | **顺序即故障转移顺序** |
| 隧道池大小 | `8` | 见下文 |
| 出站源 IP | `203.0.113.9` | 出口拨目标时绑定的地址 |

**两端都必须是你能装 agent 的机器。** 只拿到一端时用直连模式。

隧道加密买到的是**隐藏已加密流量的形状**（防 TLS-in-TLS 指纹识别），而不是"给明文加密" —— 载荷本来就是协议密文。

#### 监听端口留空 = 随机分配

留空时系统在 `10000-30000` 间挑一个该组尚未占用的端口。

为什么需要这个：一台入口机上会有多条线路，固定用 443 会让第二条起全部冲突。区间刻意避开两头 —— 1-1023 是特权端口（需要 `CAP_NET_BIND_SERVICE`），32768-60999 是 Linux 默认的 ephemeral 区间（占用它会和本机出站连接冲突）。

**注意**：这只避开本系统已知的冲突。目标机器上有没有**其他程序**占着某个端口，要等 agent 真正 bind 时才知道；绑不上会在面板的机器状态里看到错误。

#### 其他字段

**引用的是组，不是单台机器。** 组内加减机器不需要回来改线路。

**隧道池大小为什么是 8**：单条 TCP 上复用 N 条流，一次丢包会阻塞其后所有流 —— 这是有序传输的固有属性，应用层分帧消除不了。跑 8 条独立 TLS 连接并把流分散过去，一条卡住只影响约 1/8 的流量。单连接设计因此被否决。直连模式不涉及此问题，因为它只有一跳。

改完线路不用重启 agent，下次轮询会自动生效。「重建」按钮也只是递增配置版本 —— 控制面无法直接操作 agent 进程，面板如实说明而不假装这是同步动作。

### 5.5 IEPL 商家只给一端 root 怎么办

这是最常见的 IEPL 售卖形态。**入口侧没有 root 就装不了 agent，也就不可能建隧道** —— 隧道需要两端都跑程序。

所以只能用**直连模式**：

```
用户 ──▶ 商家给的国内入口 IP ══商家的专线══▶ 你的香港机 ──▶ 落地机
                                          在这里装 agent
                                          配一条直连线路
```

配置就是上面「直连转发」那一节。专线段由商家网络承载，加密与否由商家决定，你无法插手。

拿到 root 后先确认路由：

```bash
# 两块网卡的实际地址
ip -br addr

# 去落地机的流量走哪块网卡？应该是公网网卡
ip route get 233.21.21.21

# 确认专线网卡不是默认路由
ip route show default
```

如果第二条显示走了专线网卡，就填「出站源 IP」为公网网卡地址，或按 4.2 加策略路由。

`rp_filter` 也要注意：流量从专线网卡进、从公网网卡出，是典型的非对称路径，严格模式会静默丢包 —— 这是 4.3 里标为「最难排查」的那一条。

## 6. 日常运维

```bash
sudo systemctl status  tunnel-agent      # 查看状态
sudo journalctl -u     tunnel-agent -f   # 跟踪日志
sudo systemctl reload  tunnel-agent      # 重载证书，不断开隧道
sudo systemctl restart tunnel-agent      # 优雅重启，先排空连接
```

### 6.1 证书续期

自动签发的出口证书有效期为 825 天。到期前在该出口重跑当前版本的一键对接命令即可重新签发；脚本会保留本机私钥并重启服务。CA 不会因重跑部署脚本而改变。控制面需要一直保有 `ca.key` 才能签发新证书。

`systemctl reload` 发送 SIGHUP，就地重载证书。**已建立的隧道保持原有配置继续跑，新握手用新证书** —— 为装证书而断开所有隧道属于自己造成的停机。

新证书读不出来或格式不对时，重载失败、**旧材料继续生效**，续期失误不会让节点下线。

certbot 部署钩子：

```bash
#!/bin/sh
cp /etc/letsencrypt/live/exit.example.com/fullchain.pem /etc/tunnel/exit.pem
cp /etc/letsencrypt/live/exit.example.com/privkey.pem   /etc/tunnel/exit.key
chown tunnel:tunnel /etc/tunnel/exit.* && chmod 600 /etc/tunnel/exit.key
systemctl reload tunnel-agent
```

### 6.2 升级

先升控制面，再逐台升 agent。同一协议大版本内两端可以有版本差；版本不兼容时握手会带明确原因拒绝，而不是去猜。

```bash
sudo systemctl stop tunnel-agent      # 优雅排空
sudo install -m 755 target/release/tunnel-agent /usr/local/bin/
sudo systemctl start tunnel-agent     # 立刻从缓存配置恢复服务
```

### 6.3 备份

```bash
sqlite3 /var/lib/tunnel-control/control.db ".backup '/backup/control.db'"
```

**用 `.backup` 而不是 `cp`** —— 数据库跑在 WAL 模式，直接复制可能拿到割裂状态。

同时备份 `/etc/tunnel-control/config.toml` 和 `/etc/tunnel/`。**没有 CA 私钥就无法给节点重新签发证书。**

### 6.4 卸载

```bash
sudo ./scripts/uninstall.sh            # 只删程序，保留配置和数据
sudo ./scripts/uninstall.sh --purge    # 连数据库和证书一起删（需二次确认）
```

## 7. 故障排查

| 现象 | 查什么 |
|---|---|
| 机器显示离线 | `journalctl -u tunnel-agent`；`control_url` 是否可达 |
| 一键对接报 401 | 令牌已被后续的「查看命令」操作轮换，重新复制最新命令 |
| 机器没出现在组里 | agent 日志里搜 `已加入设备组`；没有则看认证失败原因 |
| 隧道一直 connecting | 出口侧日志；证书名与 `tls_server_name` 是否一致；PSK 是否匹配 |
| 握手报 `authentication failed` | 控制面配置里的 `tunnel_psk` 与 agent 拿到的不一致 |
| 线路在 agent 上没出现 | 组详情页核对配置版本；或用 `/api/nodes/{id}/config` 预览 bundle |
| `EADDRNOTAVAIL` | `ip addr show eth1`，源 IP 是否真的在本机 |
| 隧道走了公网而非 IEPL | `ip rule show`，再 `ip route get <出口IP> from <源IP>` |
| **隧道建不起来且日志无异常** | **`rp_filter`**，见 4.3 |
| 目标看到的源地址不对 | 路由的"出站源 IP" |
| `SO_BINDTODEVICE` 报 `EPERM` | 缺 `CAP_NET_RAW`，改用源 IP 绑定 |
| 高负载下连接被拒 | 先看 `LimitNOFILE`，再看 `net.core.somaxconn` |
| 对端学到错误 MAC | `arp_announce` / `arp_ignore`，见 4.5 |

### 常用诊断命令

```bash
# agent 看到的网卡
sudo -u tunnel tunnel-agent interfaces

# 配置是否合法
sudo -u tunnel tunnel-agent --config /etc/tunnel-agent/config.toml check

# 连接统计、SYN 队列
ss -s
nstat -az TcpExtListenOverflows   # 非零说明 somaxconn 不够

# 文件描述符用量
cat /proc/$(pidof tunnel-agent)/limits | grep files
```

## 8. 性能

默认配置下的大致容量：

| 并发连接 | 描述符 | agent 内存（约） |
|---|---|---|
| 1,000 | ~2,100 | 60–120 MB |
| 5,000 | ~10,100 | 200–400 MB |
| 10,000 | ~20,100 | 400–800 MB |

**第一个会撞上的限制是文件描述符。** 每条转发连接占两个（客户端 + 目标），加上隧道自身。默认 1024 的软限制会把节点卡在 500 连接左右。systemd 单元里已经设了 `LimitNOFILE=65535`。

内核参数调优见 `docs/linux-tuning.md`，每一项都写清了作用、默认值的影响、什么时候需要改、以及改了的风险。**不要照搬网上的"TCP 优化"文章** —— 大多混着过时建议（例如 `tcp_tw_recycle`，4.12 内核已移除且会破坏 NAT 后的客户端）和针对完全不同负载调出来的数值。

## 9. 安全设计要点

- **仅 TLS 1.3**，没有 1.2、没有降级路径。加密全部由 rustls + ring 完成，没有自研密码学。
- **PSK 证明**叠加在 TLS 之上：`HMAC-SHA256(psk, "tunnel-v1" || node_id || route_id || nonce)`，常量时间校验，PSK 不过网。证书签错或实验环境忘关 `insecure_skip_verify` 时，它仍能挡住未授权对端。绑定了 `route_id`，抓到的证明不能用于其他路由。
- **出口的目标地址来自它自己的配置，不来自网络**。如果目标能由 `OPEN` 帧指定，任何已认证的入口都能让出口拨向任意主机 —— 每个出口都会变成开放代理。集成测试里有一条断言 `OPEN` 载荷里不存在 target 字段。
- **拒绝信息统一**：认证失败一律返回 `authentication failed`，不区分原因，避免被当作探测预言机。
- **Argon2id** 存密码，登录按 IP 限流（Argon2 校验故意很慢，不限流的登录接口同时也是 CPU 耗尽入口）。
- **帧长度、流 ID、窗口**在分配任何内存之前校验。解码器有伪随机输入的抗 panic 测试。网络输入最多杀掉一条隧道连接，永远不会让进程崩溃。
- **密钥用专门的类型包装**，`{:?}` 只会打出 `***`；审计详情在落库前按字段名清洗，所以"创建节点"的审计条目不会存下它刚签发的 token。
